## 1. 失效模式分类

按**检测为何失效**分为七类。每条给出：现象、根因、为什么检测没抓到、如何修复、当前状态。

---

### A 类：检查式子里写进了假设

**这是最危险的一类**：检查通过不意味着"物理对"，而意味着"假设成立"。

#### A-1 `force_balance` 漏掉惯性项

| 项 | 内容 |
|---|---|
| 现象 | 加速度工况下 `force_balance` 残差恰为 **2.03 N**（= `m·a` @ 1 m/s²） |
| 根因 | 检查式写的是 `c + b − w`，而正确式是 `c + b − w − m·a`。基线 a≡0，所以该式在基线上恒成立 |
| 为何没抓到 | **检查器本身就是那个错误式的实现**。它"通过"了三年（概念上），因为它检验的正是"无惯性"这个假设 |
| 修复 | 改为 `c + b − w − m·a`，残差降至机器精度（`3.0e-15` N） |
| 状态 | ✅ 已修（`e4d46db`） |

**教训**：一个检查如果与模型共享同一个假设，它无法发现该假设是错的。

#### A-2 `prescribed_zero_acceleration` 把假设当断言

| 项 | 内容 |
|---|---|
| 现象 | 合法的加速度工况被判为 FAIL（`max_abs(acceleration)=1 m/s^2`） |
| 根因 | 检查把 `a ≡ 0` 当作**正确性条件**，而不是**工况类型** |
| 为何没抓到 | 负例套件里有一条 `acceleration_nonzero`，它**期待**这个 FAIL——即测试与错误断言互相印证 |
| 修复 | 改为 `motion_type`（只报告类型）；负例改为 `accelerated_without_inertial_term`（测真正仍存在的失败模式） |
| 状态 | ✅ 已修（`e4d46db`） |

**教训**：当负例测试**期待**一个错误的 FAIL 时，测试套件会成为错误断言的护城河。

### B 类：修复只在测试它的那个环境里成立

#### B-1 【最重要】F7 被标记为 Fixed，但只在有 `.git` 的工作副本里成立

| 项 | 内容 |
|---|---|
| 修复报告原文 | `F7 machine-specific paths — **Fixed**`："Verifier writes repo-relative paths" |
| 实际现象 | 在 `git archive` 导出的树上，`verification.json` 写成 `AppData/Local/Temp/<dir>/Models/CDFV-001/Ref-01B/results` |
| 根因 | `to_posix_relative` 用 `repository_root()` 定位仓库根，而后者**向上查找 `.git` 目录**。导出树无 `.git` → 根定位退化为模型目录 → 结果目录"看起来"在根之上 → `relative_to` 算出带 `..` 的路径 |
| 为何没抓到 | **CI 的 `actions/checkout` 永远提供 `.git`**，所以 CI 走的是成功分支。本机工作副本也有 `.git`。**五层检测全部在"有 `.git`"的环境里运行** |
| 后果 | 哈希冻结产物**不可移植**。任何拿到 tag zip 或 `git archive` 的人都看到哈希不符 |
| 发现方式 | 冷启动检查：导出 tag 到无 `.git` 目录，跑门禁 → 4 项 PASS，`drift check` **FAIL** |
| 修复 | `to_posix_relative` 把"逃出仓库根的相对路径"视为无法表达，退化为稳定目录名 |
| 状态 | ✅ 已修（`062ce86`），但**该检查尚未进入 CI** |

**这一条是本报告的核心发现。** 它说明：

> **"在我的机器上能跑"和"在别人拿到的形态里能跑"是两个不同的断言，而本项目的五层检测只覆盖了前者。**

#### B-2 F8 在合并前被违反

| 项 | 内容 |
|---|---|
| 修复报告原文 | `F8 commands dirty tracked files — Fixed` |
| 实际现象 | 在 `main` 上运行 `verify_baseline.py` 后，6 个注册产物显示为 modified |
| 根因 | `main` 当时仍用旧 `.gitattributes`（`* text=auto eol=lf`），CRLF 内容被判为"待归一化" |
| 关键点 | 那 6 个文件**字节与 HEAD 完全相同**——不是真的改了 |
| 为何没抓到 | 该状态只在 `main` 分支存在；修复在 `feat` 分支上验证过，是绿的 |
| 修复 | PR #1 合并后 `main` 获得 `* -text` 规则 |
| 状态 | ✅ 已随合并解决，但**暴露期 6 天**（10-09 至 10-19） |

### C 类：度量在测别的东西

四个指标全部属于此类。**共同特征：数值看起来合理，但语义与声称的不同。**

#### C-1 `loops_closed` 是硬编码的

| 项 | 内容 |
|---|---|
| 现象 | 两个知识更新都已定义且都有决议，`loops_closed` 仍为 **1** |
| 根因 | 代码是 `"loops_closed": 1 if closed else 0`——**从未计数** |
| 为何没抓到 | `closed` 为 True 时它返回 1，而项目长期只有 1 个闭环，**两者恰好一致** |
| 修复 | 改为"已定义且附有决议的知识更新数量"，并输出逐环明细 |
| 状态 | ✅ 已修（`bcf213e`） |

#### C-2 知识更新"被提到"就算"已产出"

| 项 | 内容 |
|---|---|
| 现象 | 我在 P004 文档里写"Knowledge Update（`KU004-001`）尚未完成"，指标立刻报 `KU ids = ['KU003-001', 'KU004-001']` |
| 根因 | 检测器只匹配 `KU\d{3}-\d{3}` 模式，分不清"计划产出"与"已产出" |
| 为何没抓到 | 无测试覆盖"前瞻性提及"这一情形 |
| 修复 | 要求定义形式 `Knowledge Update ID: KU003-001` |
| 状态 | ✅ 已修（`f157e6a`） |

**讽刺点：这个缺陷的效果正是该指标存在要防的事——虚增 `loops_closed`。**

#### C-3 决议状态匹配三个字面短语

| 项 | 内容 |
|---|---|
| 现象 | `D002-002` 记的是 `Needs CDFV acceleration profile`，被当作"未决议" |
| 根因 | 匹配列表是 `("needs cdfv experiment", "accepted", "rejected")`，字面匹配 |
| 修复 | 改为结构性判据：陈述了处置方式且不是占位词（Candidate / proposed / not yet） |
| 状态 | ✅ 已修（`bcf213e`） |

#### C-4 【最隐蔽】`unpushed` 测的是"领先 origin/main"

| 项 | 内容 |
|---|---|
| 现象 | 报 `unpushed_commits = 10`，但 5 个分支**全部已推送** |
| 根因 | 本地 `remote.origin.fetch` 是 `+refs/heads/main:refs/remotes/origin/main`——**只跟踪 `main`**。于是 `git rev-list --branches --not --remotes` 把所有其它分支的提交都算作"未推送" |
| 为何没抓到 | 命令**执行成功**，数字**看起来合理**。修复 refspec 后同一命令返回 **0**，两次都是"正确执行" |
| 后果 | `T13` 触发器（未推送即扣分）**长期假警报**；我在 10-20 日报里必须先解释才能读懂 |
| 修复 | refspec 改为 `+refs/heads/*:refs/remotes/origin/*` |
| 状态 | ✅ 已修，但**历史快照里的旧读数按旧口径记录，无法追溯更正** |

**教训**：一个度量可以"正确执行"却测量错误的东西。**只有当两个读数都出现时，差异才会暴露。**

### F 类：基准/归一化错误

#### F-1 `C_a` 未指定归一化基准

| 项 | 内容 |
|---|---|
| 现象 | 同一个物理 `m_a`，按三种基准归一化得 `C_a` = 0.118 / 0.424 / 0.637，相差近 10 倍 |

## 2. 为什么五层检测全部失效：一份归因

| 检测层 | 能发现 | **不能发现** |
|---|---|---|
| L-a 对象校验器 | schema 违规、哈希不符、路径缺失、review gate | **在别的环境里是否成立**（它自己就跑在有 `.git` 的树里） |
| L-b 基线校验器 + 18 负例 | 数据内部的力平衡、单位、单调性 | **检查式子本身是否漏项**（A 类全部） |
| L-c 12 对抗用例 | 预定义的 7 类故障 | **未预见的故障族**；生成器副作用（E-1） |
| L-d 门禁自测 13 场景 | 校验器是否还能拒绝坏对象 | **修复是否传播到默认分支**（G 类） |
| L-e CI | 在独立 OS/Python 上可复现 | **在无 `.git` 的树里可复现**（B-1） |

### 三条结构性结论

1. **所有检测都在"作者的环境形态"里运行。**
   CI 是唯一的外部环境，但它由 `actions/checkout` 提供 `.git`，
   因此**它与开发者的工作副本共享同一个关键前提**。
   → 需要一个"导出树"检测。

2. **检测与被检对象常常共享同一个假设。**
   A-1（力平衡漏惯性项）、A-2（a=0 当断言）、C-1（`loops_closed` 硬编码至 1）
   都属于"检查与实现犯同一个错"，因此彼此印证。
   → 需要**不与实现共享假设**的独立检查（如精确解、量纲分析）。

3. **"修复"与"修复生效"是两个状态，项目只追踪前者。**
   F7 与 F1 都被标记 Fixed，但 F7 只在子集环境成立，F1 只在非默认分支成立。
   → 修复记录需要**附带"在什么形态下验证过"**。

## 3. 可复用的建议

给任何采用类似"哈希冻结 + 可执行校验"方案的团队：

| # | 建议 | 对应失效模式 |
|---|---|---|
| 1 | **在无 VCS 元数据的导出树上跑一遍门禁** | B-1（最重要） |
| 2 | 检查式子必须与实现独立推导，且检查"假设是否成立"而非"假设是否被满足" | A-1, A-2 |
| 3 | 每个度量附一个**反向用例**（"若我故意让它为错，读数会不会变"） | C-1, C-2, C-3 |
| 4 | 度量改名到它真正测的东西（`unpushed` → `ahead_of_main`） | C-4 |
| 5 | 历史数据写入需**默认拒绝**，显式 `--force` | D-1 |
| 6 | 机制 id 允许退役，不允许删除 | D-2 |
| 7 | bypass 权限必须写入对外表述 | D-3 |
| 8 | 生成器不得删除它不负责生成的文件 | E-1 |
| 9 | 检查参数必须来自被检对象本身，不能来自触发事件 | E-2 |
