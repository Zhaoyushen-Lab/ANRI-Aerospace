## 2. 关键决定：不给 `.git`

### 2.1 原任务书要求 clone

`Experiment_Requests/CLEANROOM-Replication_Task.md` §1 写的是：

> "克隆下面这个仓库…… 仓库地址：`https://github.com/...` 使用分支：`main`"

### 2.2 克隆会毁掉任务前提

本仓库的 commit message **异常详细**。例如：

- `Add a cold-start CI job, and stop guessing the repository root`
  正文解释了 `F7` 只修了一半、`..` 检查不够、以及根定位的两种失败方式；
- `Measure which columns the verifier actually constrains`
  正文写明了覆盖矩阵的结论与我自己被推翻的断言；
- `Deliver the failure-mode report D-ANRI-001 promised`
  正文列出了七个失效类别。

**一个能读 `git log` 的执行者，会直接读到答案。** 而任务书 §4 明确禁止
"先读验证脚本的实现"——理由正是要保持判断的独立性。

> **结论：带历史的交付与任务的目的是自相矛盾的。**
> 不是物流妥协，是**方法上的必要条件**。

### 2.3 代价（必须承认）

| 失去的 | 影响 |
|---|---|
| `git log` / 分支结构 | 执行者无法看到演进过程；但任务书并不要求 |
| `git diff` 定位改动 | 盲测时不能靠 diff 找故障，只能靠物理关系——**这反而更接近真实审计** |
| 分支语义（`main` vs 分支） | 执行者拿到的是**单一状态**，不存在"该用哪个分支"的歧义 |

**第 4 条是意外收益**：当时 `main` 落后 22 个 commit，
若真让他 clone 再"使用 main"，他会复现一个**已知更差**的旧版本。
纯文件树消除了这个陷阱。

---


### 2.4 对方后来能访问 GitHub 了，结论仍然不变

2026-10-20 晚些时候，执行者恢复了 GitHub 访问。是否改为让他直接 clone？

**不改。** 理由与物流无关：

1. **§2.2 的泄漏论证与网络可达性无关。** clone 得到的历史里同样写着每个缺陷与修正；
2. **clone 反而更差**：`main` 落后 **27 个 commit**，任务书又指定用 `main`。
   字面执行"clone 并用 main"会让他复现一个**已知更差**的版本——
   那不是"更真实的测试"，那是测错了对象；
3. 压缩包已完成端到端验证（§4.1），换成 clone 需要重新验证一遍。

**但他的访问恢复带来一个新的风险，必须处理：他可能已经自行 clone 了。**

若他读过 `git log`，清室前提已被污染，且**无法事后消除**。
所以补充说明的第一句应当是**问他有没有已经 clone 过**，而不是继续讲怎么解压。

**这是一个"状态不可回滚"的风险**，和本项目此前遇到的"历史快照被覆盖"同类：
一旦发生就不能靠改文件修好，只能在记录里标注。

## 5. 一个过程中的失误（记录而非隐藏）

首次打包时 `make_blind_copy.py --dest X` 生成了 `X/blind-f1/`，

## 8. 首次打包曾泄漏盲测答案（发现与修正）

### 8.1 泄漏内容

`Experiment_Requests/CLEANROOM-Replication_Task.md` 末尾有一节：

> `## 附：作者自用说明（**发布给执行者前请删除本节**）`

其中包含：

| 内容 | 为什么致命 |
|---|---|
| `F1` \| 单行 `buoyancy_N` +5% \| **0.503 N** | 直接给出被改坏的列与残差 |
| "**若只做一次盲测，用 F1**" | 直接给出用的是哪一个故障 |
| "取宽松容差（比如 1 N）会放过 F1 却抓到 F3" | 直接给出正确答案的容差方向 |

**该文件随两个 zip 一起交付。** 执行者读完即可知道 `ANRI-Aerospace_faulted.zip` 里
被改的是哪个单元格，**盲测因此完全失效**。

### 8.2 为什么没被发现

**我验证了包能不能跑，没有验证包里有什么。**

- §4.1 检查了五项门禁在解压树中通过；
- §4.3 检查了答案键（`ANSWER_KEY-F1.txt`）没进包；
- **但从没检查"包内其他文档是否已经写明答案"**。

**答案键没有进包，而答案本身在包里。** 这两件事我此前当成了同一件事。

### 8.3 修正

1. 剥离作者节（**遵从该文档自己的指示**，不是我的编辑决定）；
2. 原文保存到 `Blind_Copies/AUTHOR_NOTES-Cleanroom_Brief.md`（gitignore，不随包发出）；
3. 重新生成 RO，重建两个包；
4. **复查**：两包内含 `0.503` 或 `作者自用说明` 的 `.md` 文件数 = **0**。

### 8.4 残余泄漏：`make_blind_copy.py` 仍在树里

`Benchmarks/ANRI-RV-001/make_blind_copy.py` 的 `--list` 会列出全部故障，
包括 `F1` 的名称与描述。

**但它不能移除**：它是**已注册产物**，删掉会让
`validate_research_object.py` 在执行者的第一条命令上失败，
而他会把"包不通过校验"记为一个发现。
**一个由我人为破坏的树导致的假发现，比一个已披露的泄漏更糟。**

所以它随树交付，并在此披露。

**这构成一个真实的残余风险**：任务书 §4 只禁止读"验证脚本的实现"，
而 `make_blind_copy.py` 不是验证脚本。一个较真的执行者可能认为读它不违规。

### 8.5 这一类缺陷的形态

**功能验证通过，内容却泄漏。** 与当日早间的冷启动缺陷形状相同：
那个缺陷是"门禁只在不会失败的环境里被验证过"，
这个是"包只在能不能运行上被验证过"。

两者都是**验证了一个维度，却声称验证了整体**。

## 9. 方法论声明

- **事实部分**：文件数、体积、SHA-256、门禁退出码、故障单元格差异，
  均为实测。
- **判断部分**：§2.2 "克隆毁掉任务前提"、§2.3 的取舍、§3 的剔除理由，
  **均为判断**。其中 §2.2 是本次最可能被反对的一条——
  若认为 commit message 不构成泄题，则纯文件树就是不必要的限制。
- **一个无法回避的限制**：执行者仍可能从
  `Reviews/ANRI_Failure_Mode_Report_v0.1.md` 读到大量失效分析——
  **那份文档在交付树里**。它不直接给出任务书第 3 节的答案（故障是哪一个数字），
  但会大幅降低发现难度。**本次未剔除，这是一个已知的泄漏面。**
